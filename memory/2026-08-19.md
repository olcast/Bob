### OpenClaw resolver gotcha (the part that took a loop to crack)
- OpenClaw's `image` tool infers image capability **ONLY from model-id name patterns** (`gpt-4o`, `claude-3/4`, `gemini`, `-vl`/`vision` suffixes), per OpenClaw docs. `grok-4.6` matches none → hard-classified text-only → `image` tool returned `Model does not support images: xai/grok-4.6 (resolved input: text)`.
- The schema DOES honor `"input": ["text","image"]` on a model entry. Final fix = add that field to `grok-4.6` in `openclaw.json` (`models.providers.xai.models[0]`), then a **full gateway restart**. SIGUSR1/HUP reloads did NOT flush the resolver cache — only a full process restart picked up the change.
- Also changed `agents.defaults.imageModel.primary` → `xai/grok-4.6` (fallbacks left/dropped; qwen-vl entries now dead).
- `openclaw.json` path is not writable via the `gateway` tool (protected) — edited the file directly, then restarted.

### LESSONS (durable)
1. **Vision capability ≠ API accepts images.** OpenClaw's resolver whitelists by model-id pattern, not by probing. To use a non-pattern model for vision, both declare `input:["text","image"]` AND full-restart (SIGUSR1 is not enough for the resolver cache).
2. **Verify a provider's actual model list before "switching keys."** The Qwen VL models never existed on the token-plan key — a key swap wouldn't have fixed anything.
3. **Check for stale credential-store profiles before chasing key issues** (echo of earlier Grok "key missing" false trail). `openrouter:default` also lives in the store and is now DO-NOT-USE.

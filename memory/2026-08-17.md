

## Update (~10:38-10:55 UTC) — REAL BUG FOUND: hlops skill was never actually loading in new sessions; fixed the skill root + caught a near-miss secrets leak

**Trigger:** Olivier reported that a brand-new session (different conversation) had zero awareness of the hyperliquid-ops skill and suspected prompt injection when this session referenced it. Correct instinct, real bug — not paranoia, not injection.

**Root cause (verified against actual OpenClaw docs, `docs/tools/skills.md`):** skills only auto-load from a fixed set of roots: `<workspace>/skills`, `<workspace>/.agents/skills`, `~/.agents/skills`, `~/.openclaw/skills`, bundled, or `skills.load.extraDirs`. The hyperliquid-ops skill lived at `/root/.openclaw/workspace/skills-archive/hyperliquid-ops/` — a path I (this agent) chose during the original reconstruction, and "skills-archive" is **not** one of the real skill roots. So the skill was NEVER in the `<available_skills>` block for ANY session, including this one — every "use" of it in this session happened because I manually read files by absolute path, not because the runtime recognized it as a skill. New sessions had no way to know it existed. This had been silently broken since the skill's creation.

**Fix:** `git mv` (preserved history via rename detection) the entire skill from `skills-archive/hyperliquid-ops/` to `skills/hyperliquid-ops/` — the real, highest-precedence workspace skill root. Confirmed via `ls` that the frontmatter (`name`, `description`) is valid and will be picked up by the skills loader on next session start.

**Near-miss caught during the move — Gmail secrets almost got committed to git.** The `.gitignore` had `/skills-archive/hyperliquid-ops/.secrets/` explicitly listed (from the original inbox_check.py setup), but that rule obviously didn't cover the new `skills/hyperliquid-ops/.secrets/` path. The first `git add -A` + commit picked up `gmail.env` (Gmail address + app password) as a tracked file. **Caught before push** (repo was 2 commits ahead of `origin/main`, never pushed) — added the new path to `.gitignore`, ran `git rm --cached` on the secrets file, and amended the commit in place rather than push-then-fix. Verified with `git ls-files | grep -i secret` (empty) that no secret ever left the local repo. Lesson: any future path move for a skill/data directory must double-check `.gitignore` coverage BEFORE the first `git add -A`, not after.
